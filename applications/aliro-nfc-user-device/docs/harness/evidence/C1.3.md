## Application fixes

1. **Os::Timer callbacks ran in ISR context (C1.1 `worker_lifecycle`
   kernel panic).** `platform/os/os_timer.cpp` called the stack callback
   straight from the `k_timer` expiry handler. The stack's session watchdog
   callback takes the stack mutex, so it asserted `!arch_is_in_isr()` and
   panicked.
   - Expiry now submits a `k_work` item to a dedicated `aliro_ud_timer`
     work queue. The callback runs in thread context.
   - `Release()` implements the `Os::Timer` contract in
     `include/aliro/user_device/interface.h` ("synchronously quiescent"). It
     stops the timer, then waits for a running callback with
     `k_work_cancel_sync()`. A callback that releases its own timer uses
     non-blocking `k_work_cancel()` instead of deadlocking.
   - New Kconfig: `ALIRO_UD_OS_TIMER_THREAD_STACK_SIZE` (2048) and
     `ALIRO_UD_OS_TIMER_THREAD_PRIORITY` (5).
   - New `os_timer` suite (6 cases): thread context, `Release()` waits for a
     running callback, cancels a pending expiry, self-release from a
     callback, stop/restart, pool bounds. With the HEAD timer it fails
     0/6; with the old timer the `exchange_lifecycle` timeout case also
     panics.
2. **`cli_info` isolation.** Cases shared credential/mailbox state. A
   before-each hook now aborts any pending provisioning and runs
   `aliro-ud credential reset`.
3. **Stale comments.** The `Transaction::NotifyResult` adapter comment and
   its CMake comment now describe the `Success`/`Failed`/`Aborted`
   contract. There is no behavior change.

## Integration approach

The new `exchange_lifecycle` suite extends the C1.2 setup: real worker,
real stack, and real mailbox, OS-timer, and transaction adapters. The
test Reader (`common/test_reader.*`, PSA only) gains:

- EXCHANGE command encryption (§8.3.1.8, p. 56).
- The EXCHANGE APDU (Table 8-14, p. 81).
- The CONTROL FLOW APDU (§10.2.2.1, p. 97).
- Table 8-16 request builders, 0x8C/0x87/0x8A/0x95 (p. 82), and the 0x97
  Reader status (Table 8-18, p. 84).
- A response block parser.

The expected mailbox state is checked through `Mailbox::Store::RawRead` and
`Mailbox::Sessions::GetOpenSessionCount`. The transaction outcome is checked
from the captured `Transaction` log (C1.2 method). Transport release is
checked with `Nfc::IsSessionActive` and the fake's termination count.

## Specification interpretations

1. **Response blocks are length-prefixed.** Each block in the EXCHANGE
   response (Table 8-20 and §8.3.3.5.2, p. 86) is a 2-byte big-endian length
   followed by data. The status `0x0002 || B1 || B2` (§8.3.3.5.5, p. 87) is
   therefore a length-2 block. The Reader parses the payload this way and
   requires the last block to be the status.
2. **Implementation-specific values are not pinned.** On an in-channel error
   the tests require SW 9000, exactly `00 02 B1 B2` with B1B2 ≠ 0000, and no
   read data (§8.3.3.5.5; Test Plan 7.33/7.34, pp. 83–84). Failure-process
   cases require only SW ≠ 9000 and an empty data field (§8.3.3.1,
   pp. 63–64).
3. **Counters.** Both counters start at 1 (§8.3.1.13, pp. 58–59). The AUTH1
   response uses device counter 1. The first EXCHANGE uses reader counter 1
   and device counter 2 (IVs per §8.3.1.6/§8.3.1.8, p. 56).
4. **Atomic session reads.** Inside an atomic session and in the command
   that stops it, reads return the pre-session data. Later reads return the
   final data (Test Plan 7.28, p. 78). A command outside an atomic session
   commits its writes and sets together (§8.3.3.5.4, p. 87).

## Verification matrix

| Requirement | `exchange_lifecycle` coverage |
| --- | --- |
| P1-026 | EXCHANGE commands and responses authenticate under the independently derived ExpeditedSKReader/ExpeditedSKDevice |
| P1-029 (EXCHANGE part) | Bitmap 0x0038 (data, read, write) or 0x0018 (read only) matches the rights EXCHANGE then enforces |
| P1-032, P1-033 | Reads return committed data; write/set commit; unauthorized write (read-only) and read (write-only) rejected |
| P1-034 | Single-command atomic write+set; atomic session holds one snapshot, keeps pre-session data, commits only on stop; field loss and timeout discard staged changes |
| P1-035 | Out-of-bounds, unauthorized, and wrong-length requests give the in-channel error sequence, with no partial commit |
| P1-036 | Success status only after every request succeeds; a tampered authentication tag runs the failure process with the mailbox unchanged |
| P1-037 | Final Reader success → `success`; Reader failure status → `failed`; CONTROL FLOW after EXCHANGE or AUTH failure → 9000/empty and `failed`; field loss and timeout → `aborted`; exactly one result each; transport and mailbox released |
| P1-038 | EXCHANGE after an error sequence is rejected (session keys gone); every failure ends the session |
| P1-039 | AUTH0 wrong P1/P2 and unsupported version, AUTH1 out of sequence and wrong P1/P2 → failure process, then CONTROL FLOW → `failed` |

Recovery: after field loss and after a session timeout, a new activation
authenticates, opens a new atomic session, reads the original data, and
ends as `success`.

## Result

`worker_lifecycle` passes 12 of 12 cases (previously 1 failed, 3 blocked),
and `cli_info` passes 7 of 7. No stack blocker was found at `eed34381`.

## Open items

- The `Credential::Reset`/`Delete` mailbox cascade gap (C0.1 item 1) is
  provisioning lifecycle, not EXCHANGE/CONTROL FLOW/teardown. It is not in
  C1.3 scope. The only application caller (CLI) already erases the mailbox.
  C1.4 should assign an owner.
- Chaining and extended-length EXCHANGE are stack-owned and not exercised on
  host. Physical cases are in C7.2.
- AUTH0/AUTH1 extra-tag, wrong-value, and incomplete-chaining variants of
  P1-039 are not host-exercised here. Physical Reader cases are in C7.2.
