# C3.1 — Document snapshot and persistence behavior

## Baseline

- Application: `user-device-aliro-p2-dev` at `8d96523` plus the C3.1 change.
- `ncs-aliro`: `eed34381d7c6ff6f9ad6a06024c5c8170e1db64f` (unmodified),
  selected by the local, uncommitted `west-aliro.yml` edit (`C0.1.md`).
- Toolchain: NCS v3.4.0 (`ncs4`), `west twister -p native_sim/native/64`.

## Specification interpretation

- The User Device SHALL support storage and retrieval of the Access
  Document (§7.1, p. 32) and of the Revocation Document (§7.6, p. 45). An
  Access Credential MAY be associated with either (§6.2, pp. 28–29).
  Provisioning and lifecycle management are out of scope of the
  specification (§6.2, p. 28), so capacity, replacement, deletion, and reset
  are application decisions.
- Documents are CBOR that the Credential Issuer encodes deterministically
  (§7.2, p. 32). The application stores and returns the provisioned bytes
  verbatim. Parsing and element selection for DeviceResponse (§8.4.2,
  p. 89) stay with the stack.
- The AUTH1 `signaling_bitmap` has separate Access and Revocation bits
  (§8.3.3.4.2). The stack opens both snapshots of one credential in the
  same session (`state_machine.cpp`, `OpenDocumentSnapshotsAndSignal`), so
  at least two snapshots must be open at the same time. Signaling itself is
  C6 scope.

## Public-contract mapping

- Snapshot size bound: the public
  `CONFIG_NCS_ALIRO_USER_DEVICE_MAX_DOCUMENT_SNAPSHOT_BYTES` requires a
  backend to fail `Open()` with `ALIRO_NO_MEMORY` for a document larger than
  that bound. A `static_assert` in `document_snapshots.cpp` keeps
  `CONFIG_ALIRO_UD_DOCUMENT_MAX_SIZE` at or below it. A one-off build with
  `ALIRO_UD_DOCUMENT_MAX_SIZE=2048` and the stack bound set to 1024 fails
  with that assertion.
- Snapshot capacity: `CONFIG_ALIRO_UD_MAX_OPEN_DOCUMENT_SNAPSHOTS` range is
  now 2–8 and is checked at compile time. The Kconfig help already said it
  must be at least 2.
- `Open()`: `ALIRO_INVALID_ARGUMENT` for an invalid credential handle, a
  deleted credential, an absent document, or an unknown `DocumentType`
  value. `ALIRO_NO_MEMORY` for a full table or a persisted length beyond
  the configured maximum. On every failure `outSnapshot` stays invalid and
  no table slot is held.
- `GetSize()`/`Read()` on an invalid, never-issued, or closed handle:
  `ALIRO_INVALID_STATE`, `outSize` is 0, and nothing is written.
- `Read()`: overflow-safe bounds check, plus `ALIRO_INVALID_ARGUMENT` for a
  null destination with non-zero length. A rejected read writes nothing and
  leaves the snapshot open.
- `Close()`: a repeated or invalid close does nothing. Handles increase
  monotonically, so a closed handle never refers to a later snapshot.
- `Delete()`/`Reset()`: an open snapshot keeps its bytes until `Close()`.
  A snapshot opened afterwards sees the committed state.

## Defects fixed

- A persisted document length beyond the buffer (for example, corrupted
  storage) was copied into the snapshot without a check. `Read()` then
  bounds-checked against that length and read past the snapshot buffer.
  `Open()` now fails closed with `ALIRO_NO_MEMORY`.
- An out-of-range `DocumentType` value was treated as Revocation by
  `Open()` and by `Delete()`. Both now reject it.

## Verification

The new `tests/functional/subsys/aliro_nfc_user_device/document/` suite
links the real adapter, snapshot engine, and credential store. It uses the
shared in-memory persistence and key-backend fakes; reboot is simulated by
re-running `Store::Init()` over the retained fake flash. Records the store
would not write (zero length, over-maximum length) are written straight into
fake flash through `WritePersistedSlot()`. Every test ends with zero open
snapshots.

- Configurations: default (4 credentials, 1024 B, 2 snapshots), minimum
  (1, 1 B, 2), and maximum (8, 4096 B, 8). 12/12 cases pass in each.
- Mutation: removing the length check or the type check makes
  `test_configured_maximum_and_one_over` or
  `test_invalid_handles_are_rejected`, respectively, fail. No other test
  fails.

## Open items for later slices

- `Store::DeleteDocument()` clears the in-memory record before
  `SaveSlot()`. If the save fails, the document is missing from RAM but
  still on flash, and it comes back at the next boot. Failure atomicity of
  clear/delete is C3.2 scope. The C3.1 test asserts only that an open
  snapshot survives the failure and can still be closed.
- Whether provisioning accepts a zero-length document is C3.2 scope. C3.1
  covers the snapshot engine only, using a document written straight into
  fake flash.
- Target persistence of document records is C7.1.
