## Baseline

- Application: `user-device-aliro-p2-dev` at `7cd7d83`.
- `ncs-aliro`: `eed34381d7c6ff6f9ad6a06024c5c8170e1db64f`, selected by the
  local, uncommitted `west-aliro.yml` edit recorded in `C0.1.md`.
- Toolchain: NCS v3.4.0 (`ncs4`), `west twister -p native_sim/native/64`
  over `tests/functional/subsys/aliro_nfc_user_device/`.

The host matrix is the nine twister configurations in that directory. The
`tests/functional/subsys/aliro/*` suites are Reader-side hardware tests and
are not part of this application's host matrix.

## Build repair

Before repair, 3 of 9 configurations built. The other six failed to link
because commit `1fafe37` ("P2 API update") added the `Document` and
`PersistentKey` adapters and the `Credential::Store` →
`PersistentKey::Store::DeleteAllForCredential` cascade without updating host
wiring. Stack `eed34381` also references the `Crypto` and
`CredentialSigning` adapters from objects these tests now pull in.

The repair is test wiring only; no application or stack source changed:

- `common/fake_persistent_key_persistence.cpp` and
  `common/fake_persistent_key_backend.cpp` are new host fakes for
  `persistent_key_persistence.h` and `persistent_key_backend.h`. The backend
  mirrors `persistent_key_backend_psa.cpp` with volatile PSA keys and the
  same `crypto_internal.h` resolution/registration path.
- `authorization`, `cli_info`, and `worker_lifecycle` now build the real
  `platform/crypto`, `storage/document`, and `storage/key` sources with those
  fakes. `command_timing` adds `storage/document` and `storage/key`, and
  `mailbox` adds `persistent_key_store.cpp` and `crypto.cpp`. Each test
  `Kconfig` sources the matching application Kconfig files.

## Remaining runtime failures

None is a stack blocker, and all three are application-owned. None was
fixed here, and no test was weakened. The suggested owning slices are based
on the slice titles.

1. `worker_lifecycle.test_on_timeout_termination_on` fails with a kernel
   panic: `ASSERTION FAIL [!arch_is_in_isr()]` at `kernel/mutex.c:115`.
   The application `Os::Timer` adapter (`platform/os/os_timer.cpp`)
   invokes the stack callback directly from the `k_timer` ISR. Its comment
   assumes the callback only calls `Os::QueueEvent()`. At `eed34381`,
   `UserDeviceSession::WatchdogExpiredCallback`
   (`stack/src/user_device/session.cpp:80`) first takes the stack mutex to
   lease the session, so it cannot run in ISR context. The public header
   does not state the callback execution context. However, its
   synchronously quiescent `Release()` contract and the Reader-side
   implementation (`subsys/aliro/interface_impl/os/os_timer.cpp`, which
   defers to a workqueue) both assume thread context. Owner: application
   `Os::Timer` adapter (session lifecycle, suggested C1.3).
2. `authorization.test_auth0_response_is_independent_of_window_state`
   fails because the two AUTH0 responses differ byte-for-byte. The test
   assumes the stack returns an identical empty failure response because it
   has no AUTH0 cryptography, which is no longer true. Aliro 1.0
   §8.3.3.2.6, p. 69 requires the User Device to "generate a new random
   ephemeral Access Credential key pair ... whenever sending an AUTH0
   response". The stack now does this (`hsm/state_machine.cpp:568`), so
   `credential_ePubK` differs between the two transactions. Owner:
   application test (Standard authentication, suggested C1.2). The
   window-independence property must be checked without comparing the
   ephemeral key.
3. `cli_info.test_mailbox_inspect_init_read_and_erase_on_delete` fails
   because it inspects handle 1 and gets `data_subset_configured=1
   data_subset_pairs=1`. The suite has no per-test reset. The alphabetically
   earlier `test_mailbox_data_subset_staging_and_inspect` commits handle 1
   and never deletes it. The case passes when run alone. Owner: application
   test isolation in `cli_info` (mailbox/EXCHANGE, suggested C1.3).
