# C2.3 — Persistent-key fault injection

## Baseline

- Application: `user-device-aliro-p2-dev` at `0754477` plus the C2.3 change.
- `ncs-aliro`: `eed34381d7c6ff6f9ad6a06024c5c8170e1db64f` (unmodified),
  selected by the local, uncommitted `west-aliro.yml` edit (`C0.1.md`).
- Toolchain: NCS v3.4.0 (`ncs4`), `west twister -p native_sim/native/64`.

## Specification interpretation

- Nothing here is protocol behavior. `Kpersistent` is a long-term key kept
  in non-volatile memory (§3.1, p. 23). The User Device SHOULD store it with
  the `reader_group_sub_identifier` (§8.3.1.13, p. 59). Lifecycle
  management is out of scope of the specification (§6.2, p. 28).
- Losing a record only forgoes the fast path. The stack answers a missing
  `Kpersistent` with an indistinguishable cryptogram (§8.3.3.2.6,
  pp. 69–70), and the Reader continues with the Expedited-Standard phase
  (§8.3.3.2.8, pp. 70–71). Reappearance of a record whose `Replace()`
  reported failure is also safe: the stored key is the correctly derived
  `Kpersistent` for that credential and sub-identifier.
- Key material stays inside PSA (§16.2.3, p. 185; informative). The fault
  paths only query presence, copy into PSA, and destroy.

## Fault model

The fakes in `tests/functional/subsys/aliro_nfc_user_device/persistent_key/`
route every durable transition through one gate (`fake_power_loss.h`). The
transitions are record save and erase, and durable key ownership (the PSA
copy into the persistent ID) and destruction. The gate records a trace of
the transitions. For each operation, the clean trace is asserted first and
then every transition *k* is faulted as follows:

- **before**: transition *k* fails without effect, and later ones land;
- **after**: transition *k* takes effect but reports failure, and later
  ones land. For key ownership this goes beyond the backend contract;
- **power cut before *k***: transition *k* and every later one is refused.
  The row with no remaining transition is a cut just after completion.

In addition, every presence query (`Backend::Exists`) is failed once, and
`Persistence::Init` and each slot's `LoadRecord` are failed at boot.

Every row asserts:

- the returned error;
- the record `Lookup` sees;
- the exact surviving durable key objects, with no input or temporary
  object and no double or absent destroy;
- the state recovered by the next boot, `ExpectConsistent()`, and a second
  boot with zero writes, creates, or destroys;
- a clean factory-reset teardown.

## Defect fixed

A failed record save in `Replace()` was treated as "not persisted": the
store destroyed the new key and returned an error. If the save had in fact
landed, the persisted record named a destroyed key. For a replacement, the
next boot then dropped that record and swept the old key, so the pair ended
with neither the prior nor the new record.

`Replace()` now reads the slot back after a failed save:

- **landed**: the record is committed. The old key is retired, and the call
  returns success.
- **absent**: the new key is destroyed, as before.
- **unreadable**: both keys are kept. The next `Init()` keeps whichever
  record persisted and sweeps the other key.

Restoring the C2.2 store makes 3 of the 9 new cases fail in both
configurations: the insert and replacement matrices at the "after save"
row, and the unreadable-save test.

## Fault matrix

Notation: slot 0's IDs are *C* (committed) and *S* (staged). "Prior" and
"new" are the committed states before and after the operation. "Visible" is
what `Lookup` returns right after the fault. The key counts are durable
objects immediately after the fault and after recovery. Every recovered
state holds only its record's key.

### Insert (pre-state: empty slot; new: record → *C*)

| --- | --- | --- | --- | --- | --- |
| before own *C* | error | miss | 0 | prior | 0 |
| after own *C* | error | miss | 1 (*C*, unreferenced) | prior | 0 |
| before save | error | miss | 0 | prior | 0 |
| after save | success | new | 1 | new | 1 |
| power before own / before save | — | — | — | prior | 0 |
| power after save | success | — | — | new | 1 |

### Credential-wide delete and factory reset

- Credential-wide delete pre-state: up to two records of credential A in
  slots 0–1, plus one record of credential B.
- Factory-reset pre-state: up to three records on distinct credentials.
- Trace: erase *i*, then destroy *C_i*, for each removed record in slot
  order.

| Injection point | Result | Records | Keys | Recovered |
| --- | --- | --- | --- | --- |
| before/after any step of record *r* | error | *r* follows the single-delete row; every other removed record is gone | only *r*'s key, where that row keeps it; B's key | *r* per the single-delete row; others gone; B intact |
| power before step *n* | — | — | — | record *i* gone exactly when *n* > 2*i* |
| each presence query of each visited slot (every slot for reset) | error | all removed | only the queried committed key, if its slot had a record | all removed |

### Boot recovery

Pre-state:

- slot 0: record → *S0*, plus an unreferenced key at *C0*;
- slot 1: malformed record, with keys at *C1* and *S1*;
- slot 2: record → *C2* with no key.

Trace: erase 1, erase 2, destroy *C0*, destroy *C1*, destroy *S1*.

| Injection point | `Init` | Immediate state | Recovered |
| --- | --- | --- | --- |
| before any step | error | only that step undone; the slot-0 record resolves | slot 0 only, 1 key |
| after any step | error | fully recovered | slot 0 only, 1 key |
| power before any step / after the last | — | — | slot 0 only, 1 key |
| `Persistence::Init` fails | error | nothing written; all 3 records and 4 keys remain | slot 0 only, 1 key |
| `LoadRecord` of slot *j* fails (every slot) | error | only records below *j* dropped; no key destroyed | slot 0 only, 1 key |
| each presence query fails | error | committed key kept; no key created | slot 0 only, 1 key |

### Lookup copy and double fault

| Case | Result | Immediate state | Recovered |
| --- | --- | --- | --- |
| volatile copy fails | error; outputs cleared | no temporary object; records unchanged | record resolves |
| copy outstanding at power loss | success | temporary object vanishes at reboot | record resolves; no write |
| save fails and read-back fails (insert, replacement) | error | prior visible; both keys kept | new if the save landed, otherwise prior |

At minimum capacity (1 × 1), the bulk and boot pre-states shrink to the
records that fit. For example, boot recovery is then only slot 0.

## Verification

- `persistent_key`: 2/2 configurations and 97/97 cases passed; one case
  is skipped at minimum capacity because it needs two slots. The new
  `aliro_ud_persistent_key_fault_injection` suite passed 9/9 in both.
- Full User Device host matrix: 14/14 configurations and 241/241 cases
  passed.
- `nrf54lm20dk/nrf54lm20b/cpuapp` application build: passed. It emitted
  the pre-existing `NRF_PLATFORM_LUMOS` deprecation and CMake
  `GNUInstallDirs` developer warnings; no compile diagnostic was emitted.

## Target assumptions (C7.1)

- These C2.2 assumptions still hold: single settings entries and PSA key
  creation/destruction are atomic, and presence is reported truthfully.
- After a failed `settings_save_one`, reading the entry back reflects what
  is durable.

## Open items

- A delete whose erase lands but reports failure keeps resolving until
  reboot or retry. The error is returned, the caller keeps the credential,
  and the next boot or a retry completes the delete.
- Multiple faults beyond the unreadable save outcome are not covered. An
  example is a later failed `Replace()` into the same slot in the same boot.
- The real PSA backend's own `MintVolatileHandle` cleanup, which destroys
  the copy when registration fails, is target scope (C7.1).
