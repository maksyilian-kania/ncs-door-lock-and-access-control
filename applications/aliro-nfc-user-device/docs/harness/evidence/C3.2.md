# C3.2 — Document provisioning validation

## Baseline

- Application: `user-device-aliro-p2-dev` at `2821026` plus the C3.2 change.
- `ncs-aliro`: `eed34381d7c6ff6f9ad6a06024c5c8170e1db64f` (unmodified),
  selected by the local, uncommitted `west-aliro.yml` edit (`C0.1.md`).
- Toolchain: NCS v3.4.0 (`ncs4`), `west twister -p native_sim/native/64`.

## Specification interpretation

- Provisioning and lifecycle management are out of scope of the
  specification (§6.2, p. 28). The provisioning encoding, CLI syntax,
  validation, and failure behavior are therefore application decisions.
- An Access Credential includes its optional mailbox and MAY be associated
  with an Access Document and a Revocation Document (§6.2, pp. 28–29). The
  mailbox is part of the credential, so deleting or resetting the
  credential also erases its mailbox.
- The User Device SHALL support storage and retrieval of the Access
  Document (§7.1, p. 32) and of the Revocation Document (§7.6, p. 45). A
  document is an IssuerAuth/IssuerSignedItem CBOR structure that the issuer
  encodes deterministically (§7.2, p. 32). A present document is therefore
  non-empty. The AUTH1 `signaling_bitmap` bits 0 and 1 say that a document
  can be retrieved (§8.3.3.4.2, Table 8-11, pp. 73–74), which would be
  false for an empty one.
- **Zero-length policy: rejected.** A present document must be
  1..`CONFIG_ALIRO_UD_DOCUMENT_MAX_SIZE` bytes long. To remove a document,
  use `clear-document`. This closes C3.1 hand-off item 2.
- Mailbox size limits and how they are configured are out of scope
  (§8.3.1.15, pp. 60–61). Mailbox provisioning behavior is unchanged
  (C1.4).
- Document bytes stay opaque. Deciding whether the CBOR is well formed and
  which elements to select is stack-owned (§8.4.2); the application does
  not parse documents.

## Behavior

- **Canonical payload shape** (`ValidateDocument`, `Provisioning::Parse`):
  - A present document has length 1..max.
  - An absent document has length 0 and no bytes.
  - Bytes past the declared length must be zero.
  - Each of the payload's 10 `bool` fields must be the byte 0 or 1.
  - Any violation returns `ALIRO_INVALID_ARGUMENT` from Validate, Create,
    and Update before any state changes.
- **CLI** (development provisioning surface):
  - `credential set-document <access|revocation> <length> <hex>` and
    `credential clear-document <access|revocation>` replace the two
    per-type setters.
  - A type may be staged once per transaction; a second set or clear of the
    same type returns `ERR DUPLICATE_FIELD`.
  - A wrong type, zero length, max+1, a length/hex mismatch, and non-hex
    input return `ERR INVALID_ARGUMENT`. Outside a transaction the setters
    return `ERR NO_TRANSACTION`.
  - New read-only `document inspect <handle>` and
    `document read <handle> <type> <offset> <length>` return exact
    committed metadata and bytes. Reading an absent document returns
    `ERR NOT_PRESENT`.
- **Stricter CLI parsing:**
  - Hex input is validated completely before anything is written to the
    output, so rejected input never partially overwrites a staged key or
    timestamp.
  - Signs, whitespace, and non-digits are rejected.
  - Handles above `UINT32_MAX` are rejected. Before this change, the value
    4294967297 was truncated to handle 1 on 64-bit hosts.
- **Document clear** (`Store::DeleteDocument`): it saves a copy first and
  changes RAM only after the save succeeds. Clearing an absent document
  writes nothing. This closes C3.1 hand-off item 1.
- **Credential delete:**
  - If `EraseSlot` fails, the journal is rolled back so boot recovery does
    not finish a delete that returned an error.
  - Once the slot is erased, a failed journal erase is ignored. A leftover
    journal only repeats idempotent cleanup at boot.
- **Mailbox cascade** (`Interface::UserDevice::Credential::Delete/Reset`
  adapter; closes C0.1 item 1 and the C1.4 decision 1 assignment):
  - The mailbox is erased first, and the erased record is kept in RAM.
  - If the credential delete then fails and the credential still exists,
    the mailbox is restored.
  - A mailbox erase failure is returned and the credential is not deleted.
  - Reset deletes each credential this way. It resets the store and erases
    all mailboxes only if every per-credential delete succeeded; otherwise
    it returns the first error.
  - The CLI delete/reset no longer erase mailboxes themselves; they only
    call the facade.

## Fault matrix (host)

Each row is checked immediately and again after a simulated reboot. CLI
rows (`provisioning`) compare the credential record, both documents, the
mailbox configuration and bytes, and the other credentials. Document rows
(`document`) compare both documents.

| Operation | Injected fault | Result | Committed state |
| --- | --- | --- | --- |
| create / update commit | journal save, slot save | error | unchanged; staged key destroyed; nothing staged |
| update commit | journal erase | success | new record; old key destroyed |
| document clear / document reset | slot save | error | failing document kept; reset deletes the others |
| credential delete | mailbox erase | error | unchanged |
| credential delete | journal save, slot erase | error | unchanged; mailbox restored; not finished at boot |
| credential delete | journal erase | success | deleted; slot reusable |
| factory reset | mailbox erase, journal save, slot erase | error | failing credential unchanged; others deleted with their mailboxes |
| factory reset | preferred-table save (store-wide cleanup) | error | all credentials deleted; a repeated reset succeeds |

A failed commit or an abort leaves no staged document and no open
snapshot, and the next valid transaction succeeds.

## Independent verification

Verification on 2026-09-29 **failed the slice acceptance gate** despite all
executed builds and tests passing:

- Provisioning: 1/1 configuration, 9/9 cases passed.
- Document: 3/3 configurations, 45/45 cases passed.
- Full User Device host matrix: 18/18 configurations, 295/295 executed
  cases passed; the expected capacity-dependent C2.3 case was skipped.
- `nrf54lm20dk/nrf54lm20b/cpuapp` application build passed.
- Slice, traceability, STATE, and `git diff --check` validation passed.

The tests encode behavior that contradicts the C3.2 acceptance matrix and
exit criterion. `test_reset_erases_mailboxes_and_failures_preserve_state`
expects credentials 2 and 3 to be deleted after credential 1's mailbox erase
fails, and `test_failed_document_clear_keeps_committed_document` expects one
document to be cleared after `Document::Reset()` returns an error. The slice
requires each injected persistence/commit failure to preserve the previous
credential, documents, and mailbox, and requires all failed transactions to
preserve prior committed state. Reset must therefore be failure-atomic across
the state covered by the reset transaction, and the tests must reject partial
success. No C3.2 commit was created.

## Open items for later slices

- Target persistence and real power loss between the mailbox erase and
  the credential delete are C7.1. On power loss in that window, the
  credential survives with an erased mailbox. The mailbox is never leaked
  to a reused handle.
- A double fault (the credential delete fails and the mailbox restore also
  fails) is logged, and the delete error is returned.
- Kpersistent records deleted before a failed credential delete are not
  restored. Kpersistent cleanup is C2.2-owned.
- A failed `SavePreferredTable` during the delete purge is still ignored
  (C3.3 preferred-credential scope).
- Pre-existing provisioning validation gaps that were not in the C3.2
  document scope:
  - Zero reader-group bindings are not rejected.
  - `TrustType` values above `IssuerCa` are not rejected.
  - Non-document fields are not checked for canonical zero padding.
