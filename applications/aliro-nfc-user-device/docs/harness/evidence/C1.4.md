## Decisions

1. **Owner of the `Credential::Reset`/`Delete` cascade gap (C0.1
   item 1).** The public `Credential::Reset()` contract
   (`include/aliro/user_device/interface.h`) names mailbox data explicitly.
   The spec leaves mailbox storage and Credential Issuer management
   implementation-specific (§8.3.1.15, pp. 60–61), and an Access Credential
   includes its optional mailbox (§6.2, p. 28). This is application
   lifecycle, not protocol behavior. Current state:
   - Only the CLI erases the mailbox, and only after the stack facade call
     succeeds. It also ignores the `Mailbox::Store::EraseForCredential`/
     `EraseAll` result, so `credential delete`/`reset` can print `OK` after
     a failed erase (P1-005).
   - `DeleteSlotInternal` discards the
     `PersistentKey::Store::DeleteAllForCredential` result.

   Owners:
   - **C3.2** owns the mailbox erase in the `Credential::Delete`/`Reset`
     path and propagating its failure. C3.2 already covers delete/reset
     through the development provisioning surface with failure-atomic
     results. This assignment is recorded here and in `traceability.yaml`;
     the C3.2 slice file is unchanged.
   - **C2.2** owns propagating the `Kpersistent` cleanup result. This is
     already in its scope ("propagate cleanup failures").
   - **C3.1** owns the document part. This is already in its scope.
2. **P1-031 Kpersistent clause.** The User Device looks up `Kpersistent`
   only when the Reader requests expedited-fast, and a cryptogram is present
   only then (§8.3.3.2.6, pp. 69–70; §8.3.3.2.8, p. 70). The Standard-flow
   host evidence therefore cannot exercise this clause. It is verified with
   P2-005 in C4.3, so P1-031 stays `planned`.
3. **P1-025 StepUpSK.** StepUpSK is derived in the same Expedited Standard
   procedure (§8.3.1.13, p. 59) but is only used by Step-Up SessionData. It
   is verified in C5.2, so P1-025 stays `planned`.
4. **P1-040 timing.** Appendix 15 (p. 183) says only that processing times
   SHOULD meet the performance tests defined in the Test Plan. MCP searches
   of the Test Plan found no numeric User Device NFC processing-time bound.
   C7.2 must identify any applicable bound and measure on target. Host
   `command_timing` is instrumentation only.
5. **Host gaps identified by this audit.** No current host test covers P1-009
   (≥ 16 `reader_group_identifier` per credential, §6.2, p. 28; Test Plan
   Table 4-3, p. 34), P1-010 (selection among credentials sharing a reader
   identifier, §6.2, p. 29), or P1-008 non-exportability. Follow-up harness
   maintenance added C3.3 as the host owner for P1-009/P1-010; C7.2 retains
   target acceptance. P1-008 remains assigned to C2.x, C7.1, and C7.4.
6. **Retained C1.2/C1.3 deferrals.** These stay deferred:
   - Aliro chaining (P1-015). This is mandatory for the User Device (Test
     Plan Table 4-3, p. 34).
   - Extra-tag variants (P1-016; Test Plan 7.17 and 7.23, pp. 70 and 74).
   - AUTH0/AUTH1 wrong-value and incomplete-chaining variants (P1-039;
     Test Plan 7.18, p. 70, and Table 7-47, p. 72).

   All are stack-owned and assigned to C7.2. Extended length is optional and
   not selected.
