## Integration approach

The new `standard_integration` suite drives the real `Aliro::UserDeviceStack`
through the application NFC worker, fake NFC transport, and the real
application Authorization, Crypto, CredentialSigning, Credential,
PersistentKey, Mailbox, Document, and Transaction adapters.

The Reader side is a test-only implementation in `common/test_reader.*`.
It uses PSA directly, never the application adapters, so passing results
are not self-confirming:

- The Reader is first checked against the Aliro 1.0 Specification and Test
  Plan (26-42802-001) §14.3 no-certificate transcript (pp. 175–177). The
  check covers the authentication data, Kdh, ExpeditedSKReader,
  ExpeditedSKDevice, AUTH1 decryption, and User Device signature
  verification.
- Certificate flows reuse the §14.1 Demo 1 certificate and keys (p. 169).
  They present the certificate in LOAD CERT (§8.3.3.3, p. 71) or in AUTH1
  tag 0x90 (§8.3.3.4.1, p. 72).
- Transaction notification is observed through the application
  `Transaction` adapter's log output, captured by a test log backend
  (`LOG_MODE_IMMEDIATE`, as in production).

## Specification interpretations

1. **AUTH0 responses differ per transaction.** §8.3.3.2.6 (p. 69) requires a
   new ephemeral key pair for every AUTH0 response. The C1.1 authorization
   test `test_auth0_response_is_independent_of_window_state` compared the
   whole response and so failed by design.
   - The fixed test still requires identical length, 0x86/0x41/0x04 framing
     (Table 8-5, p. 67), and status word.
   - It excludes only the 64 credential_ePubK coordinate bytes.
   - Freshness itself is asserted by
     `test_auth0_ephemeral_key_is_fresh_per_transaction`.
2. **Certificate-flow key derivation uses the issuer key.** §6.2 (p. 28)
   defines reader_group_identifier_key as the Reader System Issuer CA
   public key when certificates are used, otherwise reader_PubK. The stack
   uses the provisioned issuer key in the §8.3.1.13 salt (pp. 58–59). The
   test Reader derives keys the same way, and AUTH1 decryption passes.
3. **Certificate rejection does not reveal trust material (P1-024).**
   - A certificate from the wrong issuer and one for a group with no issuer
     key both get the same LOAD CERT status word, and both fail AUTH1 with
     6982 and an empty data field (§8.3.3.4.5–6, pp. 77–78).
   - A malformed certificate is rejected by LOAD CERT with an empty data
     field.

## Result

Two consecutive full host-matrix runs gave identical results:

- 8 of 10 configurations passed.
- 120 of 125 cases passed, with 2 failed and 3 blocked.
- There were no compiler warnings.

`standard_integration` passed 13 of 13 cases and `authorization` passed all
cases. The remaining failures are the C1.1 items assigned to C1.3,
unchanged:

- The `worker_lifecycle` Os::Timer ISR kernel panic, which also accounts
  for the 3 blocked cases.
- `cli_info` mailbox test isolation.

No stack blocker was found at `eed34381`.

## Remaining verification

- A `success` transaction result requires an EXCHANGE carrying a final
  reader status. That, and EXCHANGE parts of P1-026 and P1-029, belong to
  C1.3.
- StepUpSK (P1-025) is not externally observable before Step-Up (C5.x).
- Host commands fit short APDUs, so chaining is not exercised here. Chaining
  is stack-owned; physical chained cases are in C7.2.
