# C2.1 — Persistent-key backend semantics

## Baseline

- Application: `user-device-aliro-p2-dev` at `50f4d8b` plus the C2.1 change.
- `ncs-aliro`: `eed34381d7c6ff6f9ad6a06024c5c8170e1db64f` (unmodified),
  selected by the local, uncommitted `west-aliro.yml` edit (`C0.1.md`).
- Toolchain: NCS v3.4.0 (`ncs4`), `west twister -p native_sim/native/64`.

## Specification interpretation

- Lookup key. `reader_group_sub_identifier` exists to look up an
  established `Kpersistent` when several Readers share one
  `reader_group_identifier` (§6.2, p. 28; §8.3.3.4, p. 72). A record is
  addressed only by the exact `{CredentialHandle, reader_group_sub_identifier}`
  pair. The public `PersistentKey::Lookup` contract says the same.
- Storage. The User Device SHOULD store `Kpersistent` with the
  sub-identifier for later Expedited Fast phases (§8.3.1.13, p. 59). It is
  a long-term key kept in non-volatile memory (§3.1, p. 23). It should stay
  inside an isolated processing environment (§16.2.3, p. 185; informative).
- Lifecycle is implementation-specific. Provisioning and lifecycle
  management are out of scope of the specification (§6.2, p. 28). Capacity,
  same-pair replacement, credential-wide deletion, and factory reset are
  therefore application decisions. They are not Aliro protocol behavior.
- Out of scope for C2.1: derivation, salts, and when the stack creates or
  consumes a record. These stay with the stack. The stack treats any
  `Lookup` error as "no `Kpersistent`" (`state_machine.cpp`, fast AUTH0
  path), so the application's specific miss code has no protocol effect.

## Defined backend behavior

The application-owned outputs are documented in
`src/storage/key/persistent_key_store.h`:

- `Lookup` miss returns `ALIRO_ERROR_UNKNOWN`. A mint failure returns the
  backend error. On every failure `outRecord` is `kInvalidRecordHandle` and
  `outKeyId` is `0`, whatever the backend wrote.
- `Replace` returns `ALIRO_INVALID_ARGUMENT` for an invalid credential
  handle, a zero key ID, or a key ID that does not resolve. It returns
  `ALIRO_NO_MEMORY` when the per-credential or global capacity is reached.
  Replacing an existing pair still succeeds at capacity. On failure,
  committed records, persisted bytes, and durable keys are unchanged. The
  input key always stays caller-owned.
- `Delete` of an invalid, unknown, or already-deleted handle, and
  `DeleteAllForCredential` of a credential without records, succeed with no
  side effects. `Reset` of an empty store behaves the same.
- Record handles are never `0` and never alias a live record. Before C2.1, a
  persisted handle of `0xFFFFFFFF` made the next insert after `Init()`
  receive the invalid handle `0`.

## Verification

`tests/functional/subsys/aliro_nfc_user_device/persistent_key/` links the
real adapter (`persistent_key.cpp`) and store with suite-local fakes:

- The PSA fake accounts for input, durable, and temporary objects, counts
  every invalid or double destroy, and injects copy and mint failures.
- The persistence fake stores each record verbatim and injects save
  failures.

Every test ends with zero live fake-PSA objects and zero invalid destroys.
The suite runs at the default capacity (4 × 16) and the minimum capacity
(1 × 1). Removing the store change makes the invalid-input and
handle-wrap tests fail in both configurations.

## Security conclusion

The persisted record image holds no 8-byte window of any stored
`Kpersistent`; the suite checks this directly. Logging was inspected:

- The store and adapter do not log.
- The PSA backend logs only key IDs and PSA status codes.
- The settings backend logs only settings keys and return codes.
- The CLI has no `Kpersistent` path.

Target non-exportability of the real PSA persistent key remains with C7.1.

## Open items for later slices

These were observed but not changed here:

- `Delete`, `DeleteAllForCredential`, and `Reset` clear the in-memory
  record before erasing it. If the erase or `Backend::Destroy` fails, a
  persisted record or an orphaned durable key survives. An orphan at a
  slot's committed ID makes later inserts into that slot fail with
  `ALIRO_KEY_ALREADY_EXISTS`. Recovery and propagation belong to C2.2, and
  the fault matrix to C2.3.
- `Init()` does not validate loaded records (for example duplicate pairs or
  handles, or a missing durable key). This is C2.2 recovery scope.
