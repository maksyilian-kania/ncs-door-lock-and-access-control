# C2.2 — Crash-safe persistent-key persistence and recovery

- Application: `user-device-aliro-p2-dev` at `af6fded` plus the C2.2 change.
- `ncs-aliro`: `eed34381d7c6ff6f9ad6a06024c5c8170e1db64f` (unmodified),

- Toolchain: NCS v3.4.0 (`ncs4`), `west twister -p native_sim/native/64`.

## Specification interpretation

- `Kpersistent` is a long-term key kept in non-volatile memory (§3.1,
  p. 23). Storing it is a SHOULD, and it is bound to the Access Credential
  public key through `salt_persistent` (§8.3.1.13, p. 59).
- Lifecycle management is out of scope of the specification (§6.2, p. 28).
  The transaction model, recovery rules, and delete/reset cascade are
  therefore application decisions, not protocol behavior.
- A missing `Kpersistent` is a protocol-handled state. The User Device
  returns an indistinguishable cryptogram (§8.3.3.2.6, pp. 69–70), and the
  Reader can continue with the Expedited-Standard phase (§8.3.3.2.8,
  pp. 70–71). The stack owns that behavior. Dropping an unusable record, or
  deleting records before their credential, therefore cannot break a
  transaction. It only forgoes the fast path.
- The key should stay inside an isolated environment (§16.2.3, p. 185;
  informative). Recovery never reads or copies key material. It only queries
  presence and destroys keys.

## Durable model

Slot *i* owns one settings entry (`aliro_ud/pkey/i`) and two PSA IDs:
*C* = base + 2*i* and *S* = base + 2*i* + 1. The persisted record is
authoritative. The only PSA object the slot may own is the key its record
names.

| Durable state (slot *i*) | Reached by | Recovery rule |
| --- | --- | --- |
| No record, no key | Normal | None |
| Record → *X*, key at *X* only | Normal (*X* ∈ {*C*, *S*}) | None |
| No record, key at *C* and/or *S* | Insert interrupted after ownership; delete interrupted after erase; failed destroy | Destroy each present key |
| Record → *X*, key at the other ID too | Replace interrupted before commit (new copy) or after commit (old copy); failed retire | Destroy the unreferenced key |
| Record → *X*, no key at *X* | Not reachable by the store; external loss | Erase the record |
| Malformed, duplicate pair or handle (lower slot wins), or *X* ∉ {*C*, *S*} | Not reachable by the store; legacy or corruption | Erase the record; a foreign ID is left to its owner |

Commit points: the record save for `Replace`, and the record erase for
`Delete`, `DeleteAllForCredential`, and `Reset`. Each rule checks presence
before destroying, so a repeated boot changes nothing and never destroys
an object twice. The same sweep runs before `Replace` reuses a slot, so a
leftover key never makes a later insert fail with `KEY_ALREADY_EXISTS`.

Cleanup failures:

- A failed erase is returned, and the record and its key stay unchanged.
- A failed destroy after a committed erase is returned. The key is kept
  for the next sweep.
- A failed retire after a committed `Replace` is swallowed, because the
  stack contract makes a `Replace` error mean "not committed". The old key
  is kept for the next sweep.
- `Init` performs every step it can, then returns the first error. The
  next boot retries.

Credential cascade (`credential_store.cpp`, closing the C1.4 assignment):

- `Delete` removes the credential's `Kpersistent` records before the
  credential journal and erase. A failure is returned with the credential
  still committed.
- `Reset` first calls `PersistentKey::Store::Reset()`, which also removes
  records whose credential no longer exists, and returns its error.
- Credential mutations run under the NFC maintenance pause
  (`lifecycle.h`), so no `Replace` can race this ordering.

An interrupted bulk deletion or factory reset leaves a consistent subset of
records. There is no durable "reset in progress" marker. The operator never
saw `OK`, so a repeated reset completes the operation.

## Verification

`tests/functional/subsys/aliro_nfc_user_device/persistent_key/` gains two
suites in both capacity configurations:

- `aliro_ud_persistent_key_recovery`:
  - Every durable state above is preloaded directly.
  - A shared power-loss model cuts power after each durable write of
    insert, replacement, delete, credential-wide delete, factory reset,
    and boot recovery itself. The tests confirm that every step was
    interrupted.
  - Runtime erase, destroy, presence, and retire failures are injected.
  - Every case checks the recovered invariant, then a second reboot with
    zero writes, creates, or destroys.
- `aliro_ud_persistent_key_credential_cascade`: the real credential store
  over the shared credential fakes, covering delete/reset removal and
  failure propagation.

Results:

- `persistent_key`: 2/2 configurations and 79/79 cases passed; one case
  is skipped at minimum capacity because it needs two slots.
- Full User Device host matrix: 14/14 configurations and 223/223 cases
  passed.
- `nrf54lm20dk/nrf54lm20b/cpuapp` application build: passed. It emitted
  pre-existing `NRF_PLATFORM_LUMOS` deprecation and ETL `GNUInstallDirs`
  developer warnings; no compile diagnostic was emitted.
- Restoring the C2.1 store and credential store fails 21 (default) and 19
  (minimum-capacity) of the new cases.

## Target assumptions (C7.1)

- A single settings entry save or delete is atomic on NVS/ZMS.
- PSA persistent key creation and destruction are atomic.
- `psa_get_key_attributes` reports an absent persistent key as
  `INVALID_HANDLE` or `DOES_NOT_EXIST`. Any other status is treated as
  indeterminate and never as "absent".
- Any `Init` recovery failure makes `main()` stop boot, as for other store
  init failures.

## Open items

- C2.3: the fault matrix beyond these single-fault and power-cut cases. For
  example, a `LoadRecord` or `Persistence::Init` failure, which aborts
  `Init` before recovery.
- Not assigned: records left by pre-C2.2 firmware for an already-deleted
  credential survive until the next credential factory reset. Credential
  update with a new key leaves records derived from the old public key. Both
  only forgo the fast path (§8.3.3.2.8).
