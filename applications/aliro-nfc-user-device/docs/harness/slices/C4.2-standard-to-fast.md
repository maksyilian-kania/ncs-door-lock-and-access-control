## Objective

Verify application backend interaction across a stack-driven Standard
transaction followed by a matching Fast transaction.

## Application-owned scope

- Observe stack calls that persist `Kpersistent` for an exact
  credential/sub-identifier pair.
- Verify later backend lookup, temporary-handle ownership, and cleanup.
- Add only application-boundary integration fixtures/assertions.

## Non-goals and stack boundary

Derivation inputs, cryptogram bytes, protocol sequencing, and Fast acceptance
decisions are stack-owned.

## Required verification

Drive Standard then matching Fast through the real stack on host.

## Acceptance matrix

- Complete Standard with an independent test Reader and prove the stack
  stores one opaque record for the exact credential/sub-identifier pair.
- Independently derive the expected 32-byte `Kpersistent` and Fast
  cryptogram/session keys in the Reader fixture, then authenticate the next
  matching Fast response without exposing key bytes through application
  APIs.
- Prove the matching Fast lookup returns only a temporary handle and that
  teardown destroys it while retaining the durable record.
- Repeat matching Fast transactions without creating duplicate records or
  changing application resource counts.
- Cover backend lookup/copy failure and field loss at each application-visible
  boundary; durable state remains usable by a later transaction.
- Treat derivation, cryptogram, counter, or sequencing mismatch as a stack
  blocker, citing Aliro 1.0 §§8.3.1.12–13 (pp.57–59) and §14.4 (pp.177–179).

## Exit criteria

The Standard-created record is consumed by matching Fast end to end, all
temporary application resources are released, and any protocol discrepancy
is recorded against an exact stack revision.
