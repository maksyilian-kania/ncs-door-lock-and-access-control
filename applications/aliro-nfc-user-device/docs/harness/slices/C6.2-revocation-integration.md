## Objective

Verify application storage, transport, and lifecycle behavior for
Revocation-only Step-Up driven by the corrected stack.

## Application-owned scope

- Provision and supply a Revocation Document through the existing
  `Document` contract.
- Verify snapshot lifetime, transport delivery, transaction notification,
  and cleanup.

## Non-goals and stack boundary

Do not select Revocation elements, construct DeviceResponse, or alter AUTH1
signaling.

## Required verification

Run Revocation-only host integration through the real stack.

## Acceptance matrix

- Provision, replace, retrieve, and delete an opaque Revocation Document
  through the application surface; the public snapshot returns exact bytes.
- AUTH1 signaling observed by the independent Reader is set only when the
  corrected stack can retrieve the provisioned document; signaling policy
  remains stack-owned.
- Complete Revocation-only Step-Up, including one and multiple GET RESPONSE
  rounds, then final success.
- Cover absent/deleted document, no matching requested element, field loss,
  timeout, transport-send failure, and final Reader failure.
- Keep an open Revocation snapshot stable during replacement and release it,
  all response buffers, timers, transport state, and temporary handles on
  every path.
- Validate the resulting DeviceResponse externally; selection, CBOR, document
  ordering, SessionData, and failure sequence remain stack-owned (Aliro 1.0
  §8.4, pp.88–92; Test Plan NFC_UD_STEPUP_RD, pp.64–65).

## Exit criteria

Revocation-only success and failure paths satisfy storage, transport,
snapshot, notification, and cleanup assertions against the corrected stack.
